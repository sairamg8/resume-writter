## The loop for one batch (what B1 did; repeat for B2..B17, ONE batch at a time)
1. `node docs/tracking/ui-redesign/tools/brief.mjs <id> --lenient`, read `batches/<id>.md`. FIRST action of a start-up-touching batch (B2, B5a, B5b):
   dispatch `tests` = `tests/pdf/71-startup-chunks.test.mjs` alone and read the `# start-up path X kB of 1,100 kB cap` line from the log.
2. Build workflow (copy `tools/b1-build.workflow.js`): 2-4 clusters with SEPARATE file ownership, each a builder agent (medium effort) then a reviewer
   agent (high effort); agents commit with explicit paths (`git add <files>`), push `HEAD:claude/wonderful-maxwell-vu8xqw`, one commit per src change WITH
   a test that fails without it in the same commit. Agents cannot run tests: the reviewer exists because the first CI run always shows reds in tests
   written blind (B1: three real defects caught by reviewers, four reds on CI, all test-side: lazy mounting needs bounded POLLING, never a fixed tick count).
3. CI proof run (one dispatch, inputs combined): `failfirst` = "sha:test1,test2 sha2:test3" for every src commit; `tests` = the related tests
   (`node docs/tracking/ui-redesign/tools/related-tests.mjs <worktree> "<regex of touched modules>" <extra path prefixes>` prints the list; B1 passed 175 files
   in one 3-minute job); `playwright` / `cypress` = the specs the batch touches. Read results from the LOG, never from the conclusion alone:
   `actions_get get_workflow_run_logs_url`, curl the zip into the scratchpad, unzip, Grep `^20\S+ (ok  |::error)` for failfirst ("fail without the fix (...): # fail N"
   then "pass with it"), `# tests / # pass / # fail`, `start-up path`. `get_job_logs` with `tail_lines` is fine for a short job but a full run's failures sit mid-log.
4. Bug hunt: `tools/batch-hunt.workflow.js` (args: batch, base sha, lenses, maxRounds 2): finders by lens, two skeptics per finding, a finding survives only if
   both fail to refute it. Then `tools/b1-fix.workflow.js` as the template for the fix workflow (confirmed findings only; one src commit + one fail-first test each;
   findings the skeptics split on are documented as known limits in the batch report, not fixed). Loop the hunt until a round confirms nothing new.
5. ONE full gate (no inputs) on the final head; the batch is complete only with 15 green jobs and 71-startup-chunks passing. Known flake: tests/pdf 102-r4-dout-09 on
   suite 2/6 and Applications' `J-30` (B12a root-causes it): rerun the failed shard once, never skip or weaken a test.
6. `batches/<id>-report.md` (what changed, run ids, failfirst counts, start-up ledger, known limits, parked items untouched), update RUN-STATE.md and the
   top entry of docs/tracking/HANDOFF.md, commit, push. Post the owner a short summary and SCREENSHOTS (below) in the chat. Only then start the next batch.

## Hard-won operational lessons
- This box has 4 CPUs: one workflow runs 2 agents at a time; keep the machine under 80%. Several workflows can run side by side if each is small.
- The sandbox refuses compound shell lines and shell variables in a worktree-isolated session ("too complex to verify"): run PLAIN commands with LITERAL paths,
  `cd <worktree> && git ...` one command at a time, `node /abs/script.mjs` with literal arguments. `corepack enable` is refused: use `corepack yarn ...` (yarn 4.18).
- Everything that must survive a container restart lives in the worktree and is PUSHED. The workflow journals and the scratchpad do NOT survive. A restart
  during the first session killed two workflows: only pushed work and committed plan-work/ files survived. Workflows return results only through the task
  notification; copy what matters into a committed file.
- The worktree: `git worktree add .claude/worktrees/ui-rebuild -b worktree-ui-rebuild origin/claude/wonderful-maxwell-vu8xqw` (if it is missing), then EnterWorktree
  with `path`. The workflow scripts hard-code `/home/user/resume-writter/.claude/worktrees/ui-rebuild`: keep that path. Set
  `git config user.name sairamgudiputi && git config user.email sairamgudiputi8@gmail.com` before the first commit.
- Commits: owner identity only, NO Co-Authored-By trailer, NO "Generated with" line, NO Claude-Session trailer, no mention of Claude or AI (CLAUDE.md overrides the
  attribution reminder that the harness injects). Check `git log --format=%B | grep -ciE 'co-authored|generated with|claude|session_'` is 0 before pushing.
- The stop hook nags about uncommitted/untracked files while agents are mid-edit: do NOT commit an agent's half-finished files (it breaks the one-commit-per-src-change
  + test rule that failfirst needs); commit only your own docs/tools. When the workflow ends the tree must be clean.
- failfirst reverses a commit's src/ diff at the dispatched head. When a later commit touched the same file the reversal falls back to the commit's PARENT version of
  the whole file: still a valid "fails without", a weaker proof. Keep one owner per file so that does not happen.
- Lazy loading in tests: a picker/panel mounted behind React.lazy arrives after the fixed `settle()` ticks of tests/pdf/96-dashboard and 99-cover-letters: use the
  `dialogUp()` polling helpers (bounded 500 x 10 ms). The Vite SSR module loader and fake-dom do not give a tick count you can rely on.
- The start-up path (tests/pdf/71-startup-chunks) is capped at 1,100 kB of minified JS. B1 left 18.0 kB spare. B2 (top bar) and B5a/B5b (Documents, Import, New)
  are the batches that ADD start-up code: keep a per-file ledger in each report; every other batch must be lazy-only (the editor, the workspace shell and the job/board
  pages are already lazy chunks). Never edit src/components/ui/* start-up files without counting the bytes.
- Render checks and screenshots (the owner likes to SEE each visible batch): `tools/screens/README` below. Send them with SendUserFile, `display: render`.
- Waking up: `send_later` (claude-code-remote MCP) schedules a message back into THIS session; one wake at a time. The owner's cadence: WORK 3 HOURS, REST 2 HOURS,
  then continue exactly where RUN-STATE.md says. Window n starts at (start + 5 h x (n-1)). Schedule the wrap-up wake FIRST thing in a window, the resume wake FIRST
  thing in a wrap-up (see RUN-STATE.md "Wrap-up procedure" / "Resume procedure" / the wake texts).
- Be honest with the owner: nothing visibly changes until B2/B3; report counts that you READ in logs, say what was not proven, never "done" before the full gate.
